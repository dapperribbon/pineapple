3. Install Docker if absent: `curl -fsSL https://get.docker.com | sudo sh`.
4. ASK ME what SIWANG_BIND should be before starting the container. Default is
   127.0.0.1. This matters: Docker publishes ports via its own iptables rules in
   the DOCKER chain, which is traversed BEFORE ufw, so ufw will NOT filter a
   published port. The bind address is the real perimeter now, not the firewall.
   Do not put a deliberately vulnerable box on a public interface on your own
   judgment.
5. `cd defence/docker && sudo docker compose up -d --build`.
6. `sudo docker compose exec siwang /opt/siwang/install/verify.sh` — expect

## Specific things I could not verify — check these first if the build fails

- The build runs `install.sh` VERBATIM using a fake `systemctl` at
  docker/systemctl. If the build dies in that script, check the stub's
  _start/_stop functions before changing install.sh — install.sh is shared with
  the VM path and should stay untouched.
- Whether mariadb-server's postinst leaves a usable datadir when policy-rc.d
  blocks the service start. The stub and entrypoint both handle an empty
  /var/lib/mysql via `mariadb-install-db --skip-test-db`, but that path is
  untested.
- Whether noble's MariaDB 10.11 still ships the `mysql` / `mysqladmin` compat
  symlinks. db/setup.sh and the stub both depend on them.
- Binary paths assumed by docker/supervisord.conf: /usr/sbin/mariadbd,
  /usr/sbin/php-fpm8.3, /usr/sbin/apache2.
- Whether the cap_net_raw xattr on /usr/bin/ping survives into an image layer.
  The entrypoint re-asserts it; verify.sh checks it.
- CRLF normalisation: the repo is developed on Windows and the Dockerfile
  strips \r from copied text files. If a script dies with "bad interpreter" or
  the brochure byte-size check fails, that step is the suspect.

## Guardrails

- Never `docker compose` with privileged: true. Stages 1-3 need nothing beyond
  Docker's default capability set.
- Do not delete /etc/letsencrypt or /var/lib/mysql.
- Do not bind-mount the docroot into the container for a box students will
  touch — the mount arrives with host uid/gid and defeats lockdown.sh's
  ownership rules, which is an unintended path to writing app code.
- If you change any lab config, re-run verify.sh and re-read
  defence/docs/UNINTENDED-PATHS.md.
